# 磐石交易AI：对话优先产品交互设计

日期：2026-07-28
状态：已确认
范围：桌面端产品信息架构、对话交互、策略选择、策略插件架构、渐进式澄清和分析结果展示

## 1. 产品定义

产品名称统一为：

> 磐石交易AI

磐石交易AI是面向中国期货市场的多模态策略分析助手。用户通过自然语言
和行情截图发起分析，系统自动完成截图识别、公开行情补充、策略计算、
风险判断和结果解释。

产品不再以独立表单和静态报告页作为主流程，而是采用持续对话模式：

```text
选择策略
  -> 提交问题和截图
  -> 系统自动识别并补充公开数据
  -> 通过对话逐步澄清必要信息
  -> 生成策略结论
  -> 用户继续追问、修正、刷新或补充证据
```

第一阶段仍然是分析和决策支持系统，不直接执行期货交易。

## 2. 设计目标

本次设计解决以下问题：

- 用户提交截图后缺少持续追问入口。
- 分析结论和八步中间结果一次性平铺，信息密度过高。
- 系统自动补充的数据与用户必须提供的信息界限不清晰。
- 信息不足时容易形成没有输入入口的阻塞状态。
- 后续增加多个策略后，缺少明确的策略选择和版本管理。
- 用户无法区分解释原结论、修正事实和重新运行策略。

目标体验是：

> 对话负责交互，结论卡负责操作指导，策略链路负责建立信任，审计详情
> 负责专业披露。

## 3. 核心原则

### 3.1 对话是主界面

从第一次提交到最终结论，再到后续追问，都在同一个会话中完成。分析结果
不再是用户无法继续交互的终点。

### 3.2 系统自动补数优先

合约行情、K线、成交量、持仓量、指标、交易时间和执行周期数据，应优先
由截图识别和公开数据源获得。

系统不得要求用户手工填写能够自动获取或计算的数据。

### 3.3 只询问真正属于用户的信息

允许向用户询问的内容主要包括：

- 当前真实持仓方向。
- 持仓数量。
- 持仓成本。
- 用户设置的止损。
- 账户或单笔风险限制。
- 多张截图存在目标合约冲突时，用户实际希望分析的对象。
- 用户主动指出的事实修正。

### 3.4 结论必须由确定性策略产生

语言模型负责：

- 理解用户问题。
- 直接读取原始截图。
- 解析用户补充信息。
- 解释策略结果。

语言模型不得绕过策略引擎独立生成交易动作。最终结论必须来自确定性
策略状态机和独立风险引擎。

### 3.5 默认简洁，按需披露

默认回复只展示：

- 当前策略。
- 当前交易形态。
- 最终动作。
- 面向当前持仓的操作说明。
- 三到五条核心依据。

八步策略、输入值、公式、证据来源、置信度和版本差异通过展开操作查看。

### 3.6 策略与系统架构解耦

当前“结构确认策略”只是系统加载的一个独立策略包，不是产品架构本身。

系统核心不得：

- 写死具体策略名称。
- 写死八个步骤。
- 写死某一种指标、形态或交易方向。
- 直接依赖某个策略包的内部类和规则。
- 为增加新策略修改会话、截图、数据、风控或前端核心流程。

系统只依赖稳定的策略契约。策略通过注册表安装、启用、升级、停用和回滚。
每次分析固定使用明确的策略ID和版本，保证历史结论可复现。

## 4. 产品信息架构

桌面端采用三层结构：

```text
历史会话侧栏
  + 对话主区域
  + 按需打开的策略审计抽屉
```

默认状态下不打开审计抽屉，避免页面过于拥挤。

### 4.1 历史会话侧栏

侧栏提供：

- 新建对话。
- 历史分析会话。
- 合约名称。
- 当前策略名称。
- 最近更新时间。
- 当前结论摘要。

示例：

```text
新建分析

CF2609 · 结构确认策略
退出多仓 · 刚刚

RB2610 · 结构确认策略
等待价格确认 · 昨天
```

一个会话对应一个持续分析上下文。用户在同一会话中上传新截图或刷新行情
时，生成新的分析版本，但不覆盖历史消息。

### 4.2 对话主区域

主区域包含：

- 会话标题。
- 当前合约。
- 当前策略。
- 行情截止时间。
- 数据新鲜度状态。
- 消息列表。
- 固定在底部的输入框。

### 4.3 策略审计抽屉

用户点击“查看八步策略”时，从右侧打开策略审计抽屉。抽屉包含：

- 八步策略执行状态。
- 每一步实际输入。
- 规则编号和阈值。
- 截图证据。
- 公开行情证据。
- 字段来源和置信度。
- 与上一个分析版本的差异。
- 当前阻塞和下一触发条件。

审计抽屉展示可验证的策略依据，不展示模型隐藏思维过程。

## 6. 输入框和附件

输入框始终存在，支持：

- 输入自然语言问题。
- 直接粘贴剪贴板图片。
- 上传一张或多张截图。
- 删除或替换待发送附件。
- 补充持仓和风险信息。
- 对已有结论继续追问。

附件入口使用统一的“+”按钮。展开后提供：

```text
上传行情截图
上传执行周期截图
补充持仓截图
填写持仓与风险信息
```

截图上传前展示简短提示：

```text
建议截图包含：
合约名称、周期、完整K线、价格轴、最新时间和使用的指标。

成交量、持仓量、收盘状态和公开行情将由系统自动补充。
```

## 7. 策略选择

### 7.1 产品与策略分层

产品名称：

```text
磐石交易AI
```

当前默认策略名称：

```text
结构确认策略
```

策略内部识别的交易形态：

```text
趋势突破做多
趋势回撤做多
趋势突破做空
趋势反抽做空
区间支撑反转做多
区间压力反转做空
```

普通用户看到中文名称。内部审计记录同时保留稳定代码：

```text
TREND_BREAKOUT_LONG
TREND_PULLBACK_LONG
TREND_BREAKOUT_SHORT
TREND_PULLBACK_SHORT
RANGE_REVERSAL_LONG
RANGE_REVERSAL_SHORT
```

### 7.2 策略选择器

策略选择器位于输入框上方，作为整个会话的固定上下文：

```text
当前策略  [结构确认策略 v1.0 ▼]
```

第一次进入时默认选择“结构确认策略 v1.0”。

策略详情卡展示：

- 策略名称。
- 策略版本。
- 适用品种。
- 适用周期。
- 策略简介。
- 所需输入。
- 输出动作类型。
- 风险模型。
- 当前状态：稳定版、测试版或停用。

### 7.3 后续多策略扩展

策略列表可以扩展为：

```text
结构确认策略             稳定版
日内突破跟随策略         测试版
跨期价差回归策略         规划中
持仓量趋势策略           规划中
```

用户在已有结论后切换策略时，不覆盖原分析：

```text
你正在从“结构确认策略”切换到“日内突破跟随策略”。

系统将使用当前会话中的截图和已确认信息创建新的策略分析版本。

[使用新策略重新分析] [取消]
```

## 8. 策略插件架构

### 8.1 架构分层

系统按以下边界拆分：

```text
Conversation and UI
  -> Analysis Orchestrator
  -> Evidence and Market Data Platform
  -> Strategy Runtime and Registry
  -> Independent Risk and Action Policy
  -> Generic Result Renderer and Audit Store
```

各层职责如下：

| 层 | 职责 |
| --- | --- |
| Conversation and UI | 管理会话、附件、策略选择、澄清和结果展示 |
| Analysis Orchestrator | 编排截图识别、数据补充、策略执行和版本生成 |
| Evidence and Market Data Platform | 生成标准化、带来源的事实快照 |
| Strategy Runtime and Registry | 发现策略、校验契约、选择版本并执行策略 |
| Risk and Action Policy | 独立评估风险并把策略信号转换为持仓动作 |
| Result Renderer and Audit Store | 通用渲染里程碑、证据、变化和最终结论 |

依赖关系必须是单向的。具体策略只能依赖策略SDK和标准输入输出类型，不能
反向依赖会话页面、数据库实现、行情供应商或某个多模态模型。

### 8.2 策略注册表

每个策略通过 `StrategyManifest` 注册：

```json
{
  "strategy_id": "structure_confirmation",
  "display_name": "结构确认策略",
  "version": "1.0.0",
  "status": "stable",
  "entrypoint": "structure_confirmation:Strategy",
  "input_schema_version": "strategy-input-v1",
  "output_schema_version": "strategy-result-v1",
  "supported_markets": ["CN_FUTURES"],
  "supported_timeframes": ["1d", "60m"],
  "process_label": "八步结构确认",
  "risk_profile_id": "china-futures-risk-v1"
}
```

注册表负责：

- 查询可用策略。
- 为策略选择器提供名称、版本、简介和状态。
- 校验策略包与当前SDK是否兼容。
- 控制稳定版、测试版和停用状态。
- 将会话固定到具体策略版本。
- 支持新版本并存和快速回滚。

前端不维护写死的策略数组，只读取注册表公开的策略元数据。

### 8.3 策略运行契约

所有策略实现统一接口：

```text
describe()
  -> 返回策略元数据和能力说明

required_facts(context)
  -> 声明当前策略分支需要哪些事实

evaluate(immutable_fact_snapshot)
  -> 返回结构化策略结果
```

策略不得：

- 自己调用行情API。
- 自己读取或修改数据库。
- 自己解析HTTP请求。
- 自己生成聊天消息。
- 自己执行交易。
- 自己绕过独立风控生成最终持仓动作。

策略通过 `required_facts` 声明数据需求，数据平台负责自动获取和计算。
如果仍有缺失，澄清服务根据字段性质判断是系统重试还是询问用户。

### 8.4 标准策略输入

策略接收不可变的 `StrategyInputSnapshot`，内容包括：

```text
analysis_id
strategy_id
strategy_version
instrument
contract
market_time
normalized_market_facts
multimodal_evidence
user_confirmed_facts
position_snapshot
risk_constraints
data_quality
field_provenance
```

输入只包含标准化事实，不暴露具体数据供应商和模型实现。策略不需要知道
数据来自AKShare、交易所、Codex还是用户确认。

### 8.5 标准策略输出

策略返回 `StrategyResult`：

```text
strategy_id
strategy_version
result_schema_version
setup_code
setup_label
strategy_status
milestones[]
signal_intent
unresolved_requirements[]
upgrade_conditions[]
invalidation_conditions[]
evidence_refs[]
```

`unresolved_requirements[]` 只描述缺失的标准事实和它对策略的影响，不包含
面向用户的自然语言问题。是否自动获取、是否重试以及如何向用户提问，由
数据平台和澄清服务统一决定。

每个里程碑采用通用结构：

```text
milestone_id
sequence
label
status
result_code
result_label
rule_ids[]
evidence_refs[]
blockers[]
next_conditions[]
details
```

当前结构确认策略返回八个里程碑。未来策略可以返回不同数量和不同名称的
里程碑。会话页面和审计抽屉根据返回结构动态渲染，不能假设固定八步。

### 8.6 风控和动作边界

策略输出的是市场判断、策略信号和失效条件，不直接输出不受约束的交易
命令。

最终动作由独立策略后处理链生成：

```text
StrategyResult
  + PositionSnapshot
  + RiskConstraints
  -> Risk Engine
  -> Action Policy
  -> Final Decision
```

这样可以：

- 独立升级交易策略而不修改风控。
- 独立升级风控而不修改策略。
- 对不同策略复用相同的账户风险边界。
- 防止某个策略包绕过风险否决。

### 8.7 通用UI契约

策略不能包含React组件或页面逻辑。策略通过元数据和结构化结果描述如何
展示：

- 策略名称和版本来自 `StrategyManifest`。
- 当前形态来自 `setup_label`。
- 步骤列表来自 `milestones[]`。
- 澄清问题来自标准字段需求和澄清服务。
- 证据展示通过 `evidence_refs[]` 关联统一证据库。
- 最终动作来自独立的 `FinalDecision`。

当前产品可以把“八步策略”作为结构确认策略的展示名称，但通用组件必须
使用“策略链路”“策略步骤”等中性概念。

### 8.8 独立升级和回滚

策略升级流程：

```text
开发新策略版本
  -> 运行策略契约测试
  -> 运行历史数据评估
  -> 注册为测试版
  -> 对指定新会话开放
  -> 通过发布门禁
  -> 标记为稳定版
```

升级规则：

- 已生成的分析永久绑定原策略版本。
- 现有会话默认保持原版本。
- 用户可以主动使用新版本重新分析。
- 新旧版本允许并行存在。
- 回滚只影响新的分析，不重写历史结果。
- 策略结果必须保存输入快照和输出Schema版本。

### 8.9 新增策略流程

新增策略时只需要：

1. 实现策略SDK接口。
2. 提供策略清单和版本。
3. 声明需要的标准化事实。
4. 返回标准策略结果。
5. 提供单元测试、契约测试和评估数据集。
6. 注册并通过发布门禁。

新增策略不应要求修改：

- 对话消息模型。
- 图片上传流程。
- 多模态证据模型。
- 行情数据供应商接口。
- 用户澄清流程。
- 风控核心。
- 通用结论卡。
- 策略审计抽屉。

### 8.10 故障隔离

单个策略加载或执行失败时：

- 不影响其他策略。
- 不生成伪造结论。
- 返回明确的策略不可用状态。
- 保留输入快照和错误审计记录。
- 允许用户切换其他可用策略。

首期可以采用同进程插件实现，但契约不得依赖同进程特性。后续可以将策略
运行时迁移为独立进程或独立服务，而不改变会话、数据和UI接口。

## 9. 对话分析流程

### 9.1 首次分析

```text
用户选择策略
  -> 输入问题
  -> 上传截图
  -> 系统保存不可变输入快照
  -> Codex直接读取原始截图
  -> 系统补充公开行情
  -> 构建策略所需字段
  -> 运行八步策略
```

分析过程中在对话中展示实时进度：

```text
正在识别截图
已识别 CF2609 日线

正在补充公开行情
日线和60分钟数据已更新

正在运行结构确认策略
八步策略计算完成
```

### 9.2 信息完整

信息完整时直接生成最终结论，不再显示澄清表单。

### 9.3 信息不完整

系统先建立策略字段需求图，将缺失项划分为：

```text
SYSTEM_RESOLVABLE
系统可以通过截图、公开行情或计算解决。

USER_RESOLVABLE
只能由用户确认的账户私有信息或目标歧义。

NOT_REQUIRED
当前策略分支不需要，不能为了追求字段完整而询问用户。
```

只有 `USER_RESOLVABLE` 字段可以生成用户问题。

## 10. 渐进式澄清

澄清发生在聊天消息中，不再使用独立的“补齐数据”页面。

### 10.1 一次只问最关键的问题

系统优先询问能够解除最早策略阻塞的问题：

```text
磐石交易AI：

截图和公开行情已经完成核验。
目前只有你的真实持仓无法从公开数据获得。

请问你当前是否持有 CF2609？

你可以回复：
“多仓2手，成本16020”
“空仓1手，成本15860”
“当前空仓”
```

### 10.2 用户自然语言补充

用户不需要填写结构化表单：

```text
用户：
我有多仓2手，成本16020。
```

系统先展示理解结果：

```text
我理解为：

合约：CF2609
持仓方向：多仓
持仓数量：2手
持仓成本：16020

[确认并继续] [修正]
```

确认后，用户事实进入证据链，并重新计算受影响的步骤。

### 10.3 系统自动补数

公开数据暂时不可用时，系统必须明确说明由系统处理：

```text
60分钟公开行情暂时不可用，我正在重新连接数据源。
你不需要补充这项数据。

[重新获取行情]
```

不得显示没有动作入口的“等待补齐数据”。

### 10.4 多轮补充

如果一个用户回答仍不足以完成策略，系统继续询问下一个必要问题：

```text
已确认你持有多仓2手。

为了完成风险步骤，还需要确认：
你是否已经设置止损？

可以回复具体止损价，或者回复“未设置”。
```

每次只询问当前策略真正需要的信息，避免一次展示大量表单字段。

## 11. 最终结论消息

最终结论默认分为四层。

### 11.1 第一层：立即可执行结论

```text
策略结论：退出多仓

如果你当前持有多仓：
按策略退出当前持仓，不等待新的入场确认。

当前不建议立即建立空仓，因为执行周期价格确认尚未触发。
```

### 11.2 第二层：核心依据

```text
当前策略
结构确认策略 v1.0

当前交易形态
趋势反抽做空

核心依据
1. 市场状态为下降趋势 T-
2. 价格位于BOLL中轨下方、下轨上方
3. MACD空头动能增强
4. 当前多仓方向与策略方向冲突
5. 新空仓入场条件尚未完全形成
```

### 11.3 第三层：八步策略

默认折叠：

| 步骤 | 状态 | 结果 |
| --- | --- | --- |
| 1. 数据有效性 | 已确认 | VALID |
| 2. 市场状态 | 已确认 | T- |
| 3. 策略许可 | 已确认 | 趋势反抽做空 |
| 4. 价格位置 | 已确认 | 中轨下方、下轨上方 |
| 5. 量仓行为 | 已确认 | 持仓量增加 |
| 6. 动能状态 | 候选 | 空头增强 |
| 7. 价格确认 | 未触发 | 等待执行周期确认 |
| 8. 风险与动作 | 已确认 | EXIT |

### 11.4 第四层：审计证据

用户展开某一步后查看：

- 截图原始区域。
- 多模态识别文本。
- 公开行情数值。
- 指标参数和公式版本。
- 规则编号。
- 置信度。
- 字段来源。
- 数据截止时间。
- 上一个版本和当前版本的变化。

## 12. 结论后的持续追问

每次结论下方提供建议问题：

```text
[为什么要退出？]
[什么条件下可以做空？]
[如果我当前空仓怎么办？]
[解释第7步]
[刷新行情重新分析]
```

用户也可以直接输入任意问题。

### 12.1 解释型追问

例如：

```text
为什么不是继续持有？
```

系统读取当前不可变决策对象和策略步骤进行解释，不重新运行策略，不改变
原始结论。

### 12.2 情景推演

例如：

```text
如果价格重新站上BOLL中轨，结论会怎样？
```

系统必须明确标记为假设分析，不得将假设结果覆盖真实结论。

### 12.3 事实修正

例如：

```text
刚才识别错了，这张是60分钟图。
```

系统先展示修正后的理解，用户确认后生成新分析版本。

### 12.4 新增证据

用户上传新截图后：

- 保留原图和原结论。
- 识别新增截图角色。
- 重新运行受影响步骤。
- 生成新的结论消息。
- 展示本次变化。

### 12.5 刷新行情

用户点击“刷新行情重新分析”后：

- 自动获取最新公开行情。
- 保留原截图和已确认账户信息。
- 生成新分析版本。
- 明确显示发生变化的步骤和原因。

## 13. 消息类型

对话消息需要使用明确的产品类型：

```text
USER_MESSAGE
用户自然语言消息。

USER_ATTACHMENT
用户上传的原始图片或文件。

ANALYSIS_PROGRESS
截图识别、数据获取和策略计算进度。

CLARIFICATION_QUESTION
只能由用户解决的策略问题。

FACT_CONFIRMATION
系统对用户补充信息的结构化理解。

STRATEGY_CONCLUSION
由确定性策略和风险引擎生成的最终结论。

STRATEGY_EXPLANATION
对已有结论的解释，不改变决策。

ANALYSIS_CHANGE
新旧分析版本之间的变化。

SYSTEM_DATA_STATUS
公开数据自动获取、失败和重试状态。
```

## 14. 分析版本

每条结论必须绑定：

- 会话ID。
- 分析ID。
- 策略ID。
- 策略版本。
- 输入快照。
- 使用的截图。
- 行情截止时间。
- 数据源。
- 八步策略结果。
- 风险结果。
- 最终动作。
- 创建时间。

消息中显示简化版本信息：

```text
分析版本 3
结构确认策略 v1.0
数据截止 2026-07-28 15:00
```

用户刷新行情、切换策略、修正事实或上传新证据时，创建新版本，不覆盖旧
版本。

## 15. 数据新鲜度

会话顶部持续显示：

```text
数据截止 2026-07-28 15:00
日线已收盘
60分钟已收盘
[刷新行情]
```

当数据可能过期时：

```text
当前结论基于较早行情。
[刷新后重新分析]
```

系统不得在用户没有主动刷新时，静默修改已经生成的历史结论。

## 16. 异常和阻塞

### 16.1 图片不清晰

系统说明具体无法确认的区域，并优先尝试公开数据：

```text
截图中的合约月份无法可靠识别。
我已经尝试通过公开行情匹配，但存在两个候选合约：CF2607和CF2609。

请告诉我你希望分析哪个合约。
```

### 16.2 公开数据源失败

```text
公开行情暂时不可用，本次无法生成精确策略结论。
这是系统数据源问题，不需要你手工填写行情。

[重试获取数据]
```

### 16.3 策略条件未形成

“策略条件未形成”是有效分析结果，不是数据阻塞：

```text
当前数据完整，但没有任何交易形态满足结构确认策略。

当前操作：等待
下一触发条件：价格重新进入可交易结构。
```

### 16.4 用户信息不足

系统明确说明：

- 缺少什么。
- 为什么公开渠道无法获取。
- 影响哪一个策略步骤。
- 用户应该如何回答。

## 17. 安全与信任

- 不展示伪造的模型思维过程。
- 不允许聊天模型修改确定性交易动作。
- 不把假设推演混入真实结论。
- 不用截图坐标估算精确下单价。
- 不把公开数据缺失转嫁给用户。
- 所有用户确认事实标注为 `user_confirmed`。
- 所有模型识别事实保留图片来源和置信度。
- 所有结构化行情事实保留数据源和截止时间。
- 所有策略和风险规则保留版本。

## 18. 首期范围

首期实现：

- 对话式首页。
- 图片附件上传。
- 默认“结构确认策略 v1.0”。

- 对话内渐进式澄清。

- 八步策略折叠展示。

- 移动端适配。

## 19. 验收标准

### 19.1 对话主流程

- 首页打开后，用户立即看到对话输入框和附件入口。
- 用户不需要经过独立表单才能发起分析。
- 分析完成后，输入框仍然存在。
- 用户可以继续针对结论追问。

### 19.2 策略选择

- 默认选择“结构确认策略 v1.0”。
- 当前策略在输入框附近持续可见。
- 切换策略不会覆盖旧分析。
- 结论明确展示策略名称、版本和具体交易形态。

### 19.3 渐进式澄清

- 系统只询问 `USER_RESOLVABLE` 信息。
- 公开行情和截图可识别信息不要求用户填写。
- 每次优先询问解除最早策略阻塞的关键问题。
- 用户可以用自然语言回答。
- 系统在采用用户事实前展示理解结果。

### 19.4 结论展示

- 默认结论在首屏内能够读懂。
- 操作建议与八步策略严格一致。
- 八步中间结果完整保留但默认折叠。
- 每一步可以查看证据、来源和计算输入。
- “策略条件未形成”不会被误显示为数据缺失。

### 19.5 持续追问

- 解释型追问不会重新生成或篡改原结论。
- 新截图、事实修正、策略切换和行情刷新会创建新版本。
- 系统能够说明新旧结论发生变化的具体步骤和原因。

### 19.6 策略架构解耦

- 核心系统只依赖策略SDK和标准输入输出契约。
- 当前结构确认策略可以独立升级、停用和回滚。
- 新增一个满足契约的策略不需要修改会话、数据、风控和通用UI核心代码。
- 分析结果固定到策略ID、策略版本和输出Schema版本。
- UI可以动态展示不同数量、不同名称的策略里程碑。
- 策略不能直接访问行情供应商、数据库、HTTP请求或交易执行能力。
- 单个策略失败不会影响其他策略和历史分析。

### 19.7 桌面端布局

- 桌面端对话区域保持清晰阅读宽度。
- 图片、长合约代码和证据文本不得超出容器。
- 策略审计抽屉打开后不遮挡对话输入和关键结论。

## 20. 最终产品心智

用户面对的不是一个需要自己补数据的量化表单，也不是一个只能阅读一次的
静态策略报告。

用户面对的是一个持续工作的交易分析助手：

```text
用户提供问题、截图和账户私有信息
  -> 磐石交易AI自动获取公开数据
  -> 选择并执行确定性策略
  -> 缺少必要信息时通过对话逐步澄清
  -> 给出与每一步策略严格对齐的操作结论
  -> 允许用户继续追问、修正和更新证据
```
